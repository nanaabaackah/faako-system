# Company content and enquiry email follow-up — 2026-10-30

## What staff can manage

The existing Content section now includes About, Services, How it works, Journal,
Travel footprint, Privacy, Terms and Cookies. Existing roles and server permissions
apply. Editors prepare drafts; authorised Owners request publication. New page
slugs are explicitly allowed by both API validation and the Access-aware proxy.
No schema migration or new business-data permission is introduced.

About, Services, How it works and the policies have starter drafts based on the
client intake. **Load review draft** only replaces unsaved browser fields; saving
and publishing remain explicit. Resolve policy review requirements before publication.
The personal onboarding Gmail contact is excluded from public copy.

The portal demo exposes the same new section choices, article/country fields and
review-draft loader. Edits remain in memory and reset on reload. Its three sample
country totals match the website demo. The website demo shows the company/service
preview, journal sample, contact controls and cookie preferences. Demo preferences
use `twe-demo-cookie-consent-v1`, never the live-site consent key, and cannot load
analytics. These changes appear when this branch's apps are built/deployed; they
do not synchronise a demo draft into the public website.
The website demo includes a sandboxed, expandable preview rendered by the same
pure server-side email template. It uses synthetic contact text and local brand
assets, and never invokes Resend. No authentication/database/configuration module
is imported into the public site or browser bundle by that renderer.

## Journal and footprint publication

Journal is one versioned collection of up to 20 articles, each with a unique URL
name, title, excerpt, date and plain-text body. Publishing the journal publishes
the saved collection; removing an article and publishing withdraws its static URL
(404 afterward). This intentionally shares one revision/publication boundary;
individual article scheduling, rich HTML and per-article media are not included.
Article URLs are `/journal/<slug>`, generated by Astro only from the approved
snapshot. Saved drafts never generate public routes. Existing SEO/canonical,
noindex and sitemap checks continue to apply.

Travel footprint stores verified combined country totals in the same immutable
content revisions. Use completed plus confirmed upcoming activity, one row per
country; Tanzania includes Zanzibar. The API rejects demo status, duplicate
countries and invalid totals. Public homepage, dedicated page and compact footer
read the same published records and logarithmic scale. The map and country list
remain usable without JavaScript. No traveller identity or private itinerary is
included. Empty data stays uncoloured with the existing unavailable message.

The portal imports only a small country-name/code list, not boundary geometry.
Validation tests keep the API list, country options and map coverage aligned.

## Contact, privacy and email

The public WhatsApp button uses +233 20 838 7020 at bottom left; back-to-top is
bottom right. Controls meet the 44px target minimum and are hidden while the
cookie notice is open, leaving the privacy choice unobstructed. They work as links
without JavaScript. Icons are local assets; provenance is in `public/brand/social`.

Cookie preferences allow essential-only, optional analytics and a saved custom
choice, with reopening through the footer. Analytics stays gated by the existing
shared consent loader and a published privacy page. No embedded social trackers
are introduced. Search Console is separate from the Analytics tag and is described
as search-performance reporting, not as an analytics cookie category.

Modern Concierge email contains the logo, public company identity, social icon
links and automatic-message notice, with a plain-text alternative. Inline email
styles are required for email-client compatibility; website styling remains in CSS.
See `email-test-flow.md` for final routing and obsolete variable removal.

Deploy public icon assets before enabling the new email worker version: mail
references the canonical public HTTPS logo/icon URLs. Preview captures can replace
these URLs with local assets; deployed availability still needs checking. Existing
attempted notification payloads with old routing require operator review and are
not rewritten under an existing idempotency key.
