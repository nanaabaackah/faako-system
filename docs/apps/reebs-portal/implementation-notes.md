# REEBS Portal Implementation Notes

## Purpose

Capture technical notes, open questions, cleanup targets, and risks for REEBS Portal without changing application behavior.

## Known technical notes

- The app includes a React admin portal, an Express API wrapper at `apps/reebs-portal/backend/server.js`, legacy function handler source under `apps/reebs-portal/netlify/functions`, Prisma schema/migrations, and deeper local app docs under `apps/reebs-portal/docs`.
- Portal and website frontends should use `VITE_API_BASE_URL=https://api.reebspartythemes.com` in production. The shared `patchOrganizationFetch` compatibility layer maps legacy `/.netlify/functions/*` browser calls to `/api/*` on the configured API host and keeps credentials included for same-site API cookies.
- Role assignment includes Owner, Admin, Manager, Staff, Warehouse, Driver, and Water, with legacy values normalized to Staff.
- Inventory compatibility still depends on legacy source category and specific category relationships.
- Variant-aware order, booking, scheduling, and invoicing flows should preserve `variantId` and `variantLabel`.
- Secrets must stay out of `VITE_*` values.
- `src/config/adminModules.js` defines the REEBS admin module registry for home, POS, orders, bookings, inventory, customers, delivery, finance, reports, team, settings, and detailed child navigation entries.
- `src/config/adminNavigation.js` adapts the registry into the current sidebar and bottom navigation without changing route guards, backend access, or data behavior.
- Registry metadata includes group, status, visibility, and state fields for future grouped rendering and module exposure controls, plus child modules for current detailed routes that should not be consolidated yet.
- Hidden modules are filtered out of sidebar and bottom navigation. Disabled, internal, coming-soon, and experimental metadata is currently visual only and does not block routes, redirect users, or change backend access.
- The admin route shell uses shared ERP shell/page-content/status-badge wrappers from `@faako/ui`, but REEBS-specific sidebar behavior, bottom navigation, search, notifications, auth, pages, and workflows remain app-owned.
- Shared shell placeholders for offline/sync/notifications/org switching are available structurally only. REEBS production behavior should stay app-owned until backend-owned shell metadata exists.
- Team navigation is the first consolidation implemented: `/admin/users`, `/admin/employees`, `/admin/directory`, `/admin/hr`, `/admin/roles`, and `/admin/timesheets` now resolve visually through the Team sidebar module while all routes remain intact.
- Settings navigation consolidation is implemented in registry metadata: `/admin/settings`, `/admin/advanced`, `/admin/website-template`, `/admin/inventory/products`, and `/admin/inventory/templates` resolve visually through the Settings module while existing routes and redirect targets remain intact.
- Bookings navigation consolidation is implemented in registry metadata: `/admin/bookings`, `/admin/rentals`, and `/admin/schedule` resolve visually through the Bookings module while existing routes, page logic, booking workflows, rental workflows, schedule workflows, stock behavior, payments, and receipts remain intact.
- Finance consolidation is planning-only in `finance-consolidation-plan.md`. The plan covers order payments, order receipts, invoice documents, expenses, accounting journals, reports, POS/order touchpoints, data dependencies, and security risks before any Finance grouping implementation happens.
- Finance navigation grouping is implemented in registry metadata: `/admin/accounting`, `/admin/expenses`, and `/admin/invoicing` resolve visually through the Finance module while payment recording, receipt generation, invoice generation, POS logic, order balance calculations, accounting behavior, APIs, permissions, and routes remain unchanged.
- `order-payment-receipt-workflow-review.md` maps REEBS order origins, POS payment flow, booking-linked orders, order payment ledger behavior, order receipt generation, invoice document flow, balance calculations, stock commitment timing, duplicated receipt/invoice concepts, and future shared package extraction order.
- Order payment receipts and invoice document receipts are separate source-of-truth concepts today. Do not merge them without a documented receipt ownership decision and migration/audit plan.
- `docs/platform/shared-payment-receipt-architecture.md` defines the planning-only target architecture for future shared payment, receipt, finance, and audit packages. REEBS-specific POS, booking, rental, party-item, delivery/setup, stock, and receipt-source boundaries remain app-owned until separate implementation work.
- `@faako/finance` now provides shared payment/receipt constants, pure display helpers, normalization helpers, display-safe balance helpers, metadata helpers, and receipt presentation helpers. REEBS consumes it only in order UI currency/payment-label display helpers; current payment strings used for saves, receipt generation, stock side effects, and order balance logic remain app-owned.
- `@faako/notifications` now provides shared notification constants, customer-safe message templates, channel availability helpers, and user-triggered share link helpers. REEBS consumes it only in the order receipt preview for copy summary, email draft, and WhatsApp draft actions; backend receipt delivery, Resend/email behavior, payment/order writes, receipt persistence, and customer records remain app-owned.
- `@faako/offline-sync` now provides shared offline constants, queue storage helpers, local draft helpers, retry metadata helpers, online/offline hooks, and passive status UI. REEBS consumes it for the admin shell online/offline indicator, Store Mode/manual payment draft recovery, queued Store Mode POS order creation, and queued manual order payment recording.
- Store Mode POS drafts are browser-local only. They preserve cart lines, minimal selected customer draft data, customer contact, payment method/reference, discount, and cash received for refresh recovery, then clear after successful online sale or cancellation.
- Store Mode POS can queue offline order creation as `CREATE_POS_ORDER`. The queued payload includes the idempotency key, order payload, minimal customer draft, user/org scope, and pending status. Sync resolves the customer through the existing customer endpoint and posts to the existing order endpoint when online.
- Queued POS sync marks stock-related failures as conflict/needs-review placeholders. Staff must treat needs-review sales as unresolved until the server accepts the sale; no final receipt number exists while the queue item is pending.
- Manual payment drafts remain browser-local work-in-progress state. Order detail and orders board payment forms preserve unsent amount/method/provider/reference/phone/notes fields and clear after successful online payment recording, queued offline payment creation, or cancellation.
- Manual order payments can queue offline recording as `RECORD_PAYMENT`. The queued payload includes the order reference, amount, payment method, provider/reference/phone/notes, idempotency metadata, user/org scope, and pending status. Sync posts to the existing `orderPayments` endpoint when online.
- Queued manual payment sync marks auth, permission, duplicate, invalid order, closed order, already-paid, and balance-related failures as needs-review placeholders. Staff must treat needs-review payments as unresolved until the server accepts them; no final receipt number, balance update, accounting journal, stock side effect, or audit record exists while the queue item is pending.
- Inventory stock adjustments can queue offline as `ADJUST_STOCK`. The queued payload includes the inventory item reference, optional variant reference, adjustment amount, adjustment type, optional notes/reference/sold month, idempotency metadata, user/org scope, and pending status. Sync posts through the stock API endpoint when online.
- Queued inventory adjustment sync marks auth, permission, deleted item, invalid variant, insufficient stock, duplicate, rental, booking-reservation, validation, and stock-related failures as needs-review placeholders. Staff must treat needs-review adjustments as unresolved until the server accepts them; no server inventory mutation, stock movement, booking reservation change, or audit record exists while the queue item is pending.
- Booking create/edit/status actions can queue offline as `CREATE_BOOKING`, `UPDATE_BOOKING_DETAILS`, and `UPDATE_BOOKING_STATUS`. The queued payload includes the booking reference when present, selected customer reference/details, event date/time, selected items, venue/delivery location, status action, idempotency metadata, user/org scope, and pending status. Sync posts through the bookings API endpoint when online.
- Queued booking sync marks auth, permission, customer, availability, date, unavailable item, completed/cancelled booking, invalid variant, and booking conflict failures as needs-review placeholders. Staff must treat needs-review booking actions as unresolved until the server accepts them; no server booking creation/update, rental reservation change, payment change, receipt generation, delivery/setup change, or audit record exists while the queue item is pending.
- Shared ERP notification/alert adoption (ERPNotice, ERPAlert, ERPBanner, ERPSyncAlert, ERPOfflineNotice) was reviewed and left pending. REEBS notice/alert candidates are near POS, payments, receipts, bookings, inventory, auth/session-sensitive flows, and offline queue workflows. Adoption should proceed surface-by-surface with a separate visual and workflow check for each placement before migrating away from app-owned notice markup.
- Admin Workspace Offline Sync now includes the shared `SyncReviewPanel` from `@faako/offline-sync`. It summarizes local REEBS queue items by user/org scope, shows pending/failed/conflict/needs-review/retrying/cancelled/resolved counts, displays only safe metadata and last error text, and exposes local retry, cancel, and mark-resolved controls.
- Sync Review retry re-arms local queue items for existing app-specific sync paths; it does not bypass server endpoints, generate receipts, update balances, mutate stock, reserve bookings, or alter online business logic. Cancel and mark-resolved are local review states only and must not be treated as proof of server completion.
- `docs/platform/codebase-cleanup-audit.md` flags REEBS cleanup hotspots including large admin pages, duplicate admin/public CSS patterns, repeated display helpers, candidate legacy components, and production-sensitive POS/order/payment/booking/inventory/offline-sync boundaries.
- `@faako/org-settings` is available as a pure data/helper foundation. It provides normalizeOrganizationSettings, display helpers, and safe metadata helpers. No REEBS Portal code uses it yet — wiring requires a backend org settings API endpoint scoped by authenticated session organizationId. Safe REEBS adoption path: display businessName, currency, and timezone in a read-only org section of the admin settings panel; use getOrganizationDisplayName/getOrganizationContactInfo in @faako/notifications receipt templates; use getOrganizationCurrencySymbol in @faako/finance receipt helpers. Auth, POS, payments, bookings, inventory, receipts, orders, offline queue behavior, and database schema must not be changed during org settings wiring.
- The shared `ERPActivityFeed` component from `@faako/ui` is available but REEBS Portal adoption was deferred. The existing app-owned `ActivityPanel` in AdminWorkspace (classes `aw-activity-*`) is the live operational feed and must not be replaced without a separate review. Safe future candidates: admin settings surface or a dedicated admin audit log view where data is read-only and not near payment, booking, POS, inventory, or auth flows.
- Safe Cleanup Wave 1 removed only confirmed unused imports/obsolete lint comments, adjusted a catalog media lint helper equivalently, and excluded generated/runtime folders from REEBS ESLint scans. Remaining hook/Fast Refresh warnings are intentionally parked because they could affect runtime behavior if changed casually.
- The shared ERP shell (`erp-shell.css`) now uses `100dvh` (with `100vh` fallback) for shell frame, sidebar, and sidebar panel height; bottom nav now positions with `env(safe-area-inset-bottom)` for notched phones; bottom nav buttons gained touch targets and keyboard focus-visible. These are CSS-only improvements in `@faako/theme`; REEBS-specific bottom navigation, sidebar behavior, auth, POS, bookings, payments, and workflows are unchanged.
- Shared ERP modal/drawer `max-height` values now use `dvh` (with `vh` fallbacks); dialog close buttons gained minimum touch target sizing; dialog body gained `overscroll-behavior: contain`. These changes are in `@faako/ui` and do not affect REEBS modal state, cancel/confirm semantics, save/delete/submit handlers, or workflow side effects.
- `ui-erp-field__control` in `@faako/ui` now sets `font-size: 1rem` to prevent iOS Safari auto-zoom. This does not affect REEBS form validation, submission behavior, API calls, auth, or booking/payment/inventory workflows.
- `@faako/audit` now provides shared audit event constants, safe actor/org reference helpers, sensitive metadata normalization, sync outcome helpers (createSyncAuditEvent), settings helpers (createSettingsAuditEvent), and display formatting helpers. REEBS Portal does not yet consume @faako/audit at runtime; no REEBS app code, auth, POS, bookings, inventory, receipts, payments, roles, or database schema changed. Low-risk adoption starting points: createSyncAuditEvent for POS order, payment, inventory, and booking queue sync outcomes; createSettingsAuditEvent for settings saves; AUDIT_ACTION_TYPES for future server-side Netlify Function audit log writes via @faako/logger.

## Open questions

- Which private-beta workflows should be considered launch-blocking before each deploy?
- What is the canonical rollback plan for failed migrations or production data relinking?
- Which admin modules are stable enough to graduate from private-beta monitoring?
- Which module visibility rules should become registry metadata before any database-backed enable/disable work starts?
- Which REEBS modules should become app-specific consolidated modules before module toggles are exposed to admins or orgs?
- Which REEBS shell controls should eventually move into shared wrappers without losing app-specific search, notifications, or role behavior?
- Should Team eventually become a deeper workspace with tabs for Directory, HR, Roles, and Timesheets, or remain a grouped navigation entry?
- Should inventory product/template admin configuration eventually become Settings tabs, Inventory child tabs, or a dedicated configuration surface?
- Should Bookings eventually become a deeper workspace with a shared booking calendar, linked order/payment flow, rental return workflow, and delivery/setup schedule?
- Should future Finance grouping show POS/orders as cross-links, child items, or keep them as separate operational modules with Finance summaries only?
- Should Vendors/Documents join the visible Finance grouping in a later pass, or remain standalone privileged modules until document/vendor workflows are reviewed?
- Which receipt source of truth should own future shared receipt numbering and delivery: `OrderReceipt`, invoice documents with `documentType: receipt`, or a new platform receipt model?
- Should payment provider confirmation become a separate state machine before any shared payment ledger extraction?
- Which REEBS payment/receipt constants can be safely shared first without implying shared persistence, gateway behavior, or receipt numbering?
- Which REEBS notification templates should become server-rendered only after customer preferences, notification audit logs, and opt-in/consent rules are defined?

## Risks to monitor

- Permission drift between frontend navigation and backend enforcement.
- Receipt, invoice, accounting, and revenue-recognition regressions.
- Inventory and variant mismatches that affect bookings, orders, or fulfillment.
- Production data changes from migrations, imports, relinks, and seed scripts.
- Future registry wiring into access checks, route guards, database-backed toggles, org-level config, or SaaS plan gating could affect authenticated navigation and must be reviewed separately.
- Shared shell wrapper changes can affect private-beta navigation density, topbar spacing, or mobile bottom-nav ergonomics even when data behavior is unchanged.
- Future deeper Team consolidation could accidentally blur standard versus privileged team workflows if frontend grouping is mistaken for permission enforcement.
- Settings grouping could confuse owner/admin users who expect inventory product/template admin routes under Inventory; monitor navigation feedback before any deeper page consolidation.
- Bookings grouping could confuse users who expect Rentals under Inventory or Schedule as a separate admin item; monitor navigation feedback before any shared calendar or rental workflow consolidation.
- Finance consolidation could cause payment/receipt/source-of-truth drift if order payments, invoice-document receipts, reports, and accounting journals are grouped before their ownership boundaries are explicit.
- Finance grouping can make Expenses/Invoicing less direct in the flat sidebar; monitor private-beta feedback before adding a deeper Finance workspace or child navigation.
- Shared payment or receipt extraction could create duplicate payments, stale receipts, receipt-number drift, stock/payment mismatches, or accounting journal regressions if order payment side effects are moved before idempotency and audit behavior are defined.
- Shared architecture work could be mistaken for shared runtime behavior; keep REEBS payment writes, receipt numbering, stock commitment, and invoice document behavior unchanged until app-specific adapters are proven.
- Shared notification templates could be mistaken for automated delivery. Current REEBS use is user-triggered receipt summary copy/email/WhatsApp drafts only; do not send automated messages or include internal notes, audit metadata, raw database IDs, secrets, or environment values in customer messages.
- Offline queue constants and local draft helpers could be mistaken for broader enabled offline workflows. REEBS currently queues POS order creation, manual order payment recording, inventory stock adjustments, and booking create/edit/status actions only; it must not queue delivery updates, unrelated customer writes, or deeper payment/receipt/inventory reservation side effects until server-side permission rechecks and conflict handling exist.
- Queued POS sales may fail when stock changes before sync. The current placeholder marks stock-like failures as needs-review/conflict and keeps the queue item local; do not auto-deduct stock or generate final receipts offline.
- Queued manual payments may fail when balances, permissions, order status, or duplicate payment context changes before sync. The current placeholder keeps failed/needs-review queue items local; do not create final receipts, update balances, or trigger accounting effects offline.
- Queued inventory adjustments may fail when item records, variant stock, rental restrictions, reservations, or permissions change before sync. The current placeholder keeps failed/needs-review queue items local; do not mutate stock, create stock movement records, or override booking reservation checks offline.
- Queued booking actions may fail when availability, selected items, customer records, status, permissions, or completed/cancelled state change before sync. The current placeholder keeps failed/needs-review queue items local; do not reserve rental inventory, create delivery/setup changes, or treat offline booking status as server-confirmed.
- Sync Review can make local queue state easier to change. Operators should treat retry as a request for existing server validation, and treat cancel/mark-resolved as local housekeeping after manual review, not as a production data write.
- Local drafts can contain customer contact or payment reference text entered by staff. Keep the stored payload minimal, scoped by app/org/user/order where possible, and clear drafts after successful online submission.
- Cleanup work could accidentally alter live private-beta workflows if large admin files are split before route, role, payment, booking, inventory, receipt, and offline queue checks exist.
- Shared form wrappers could be mistaken for shared validation or submit behavior. Keep REEBS form state, validation rules, backend checks, role behavior, API calls, local draft behavior, and workflow side effects app-owned until a dedicated form-by-form review is complete.
- Shared modal/action wrappers could be mistaken for shared confirmation or destructive-action behavior. Keep REEBS modal state, cancel/confirm semantics, save/delete/submit handlers, backend checks, role behavior, API calls, local draft behavior, and workflow side effects app-owned until a dedicated modal/action review is complete.
