# Dev ERP Implementation Notes

## Purpose

Capture technical notes, open questions, cleanup targets, and risks for Dev ERP without changing application behavior.

## Known technical notes

- The app combines a Vite frontend with an Express and Prisma backend.
- Dev ERP is fully live and contains real operational data.
- `backend/server.js` owns runtime composition while feature routes are organized into focused slices.
- Site/app monitoring now reads from `getMonorepoMonitoringSites(process.env)` in `@faako/config`. Every registered app workspace is represented. Hosted apps are fetched through a bounded worker pool controlled by `SITE_STATUS_CONCURRENCY`; optional System Starter, UI Workbench, and backend/API surfaces remain tracked by the registry. Dev ERP filters API and internal-only surfaces out of the website/portal page list, and promotes API surfaces into System Status rows. Optional URL overrides are documented in `apps/dev-erp/README.md`.
- Stroane Web emits monitoring metadata for the public storefront, `portal.stroanesolutions.com`, and the catalogue backend (`/health`, `/api/catalogue/products`, `/api/catalogue/categories`, `/api/products`, `/api/categories`). The backend surface remains visible in System Status as `Not configured` until `STROANE_API_BASE_URL`, `STROANE_BACKEND_BASE_URL`, or monitoring-process `VITE_BACKEND_BASE_URL` is configured.
- Root script `pnpm run monitoring:check` scans `apps/`, compares current app directories against `@faako/config` monorepo app registry metadata, verifies monitoring-enabled apps resolve into monitoring output, and prints only app keys/counts. Use it when adding apps so Dev ERP monitoring does not drift back to hardcoded local lists.
- `@faako/config` now includes app-mode helpers for `normal`, `degraded`, `read_only`, and `maintenance`, and `@faako/ui` includes generic/ERP maintenance/read-only/degraded presentation wrappers. Dev ERP has not wired these into runtime behavior yet. Any future Dev ERP read-only or maintenance mode must pair frontend banners with backend/API write guards before relying on it during migrations or risky deployments.
- The frontend boots auth state from `/api/auth/session`.
- Session state is cookie-based, with the shared API client handling credentials, CSRF headers, JSON parsing, normalized errors, and one safe `/api/auth/refresh` retry before clearing the local session on expired access cookies.
- Hosted frontend/API deployments currently support direct browser traffic to the Railway `*.up.railway.app` URL. Set frontend `VITE_API_BASE` to that API URL, use `AUTH_COOKIE_SAME_SITE=none`, `AUTH_COOKIE_SECURE=true`, and retain an explicit `CORS_ORIGINS` frontend allow-list. Safari blocks third-party cookies by default, so a same-site custom Railway API hostname such as `api.dev.example.com` beside `dev.example.com` is required for reliable Safari login persistence; register it on Railway, point its DNS CNAME to Railway's provided target rather than Cloudflare Pages, and use `AUTH_COOKIE_SAME_SITE=lax`. For local development, keep `VITE_API_BASE=""`, `AUTH_COOKIE_SAME_SITE=lax`, and `AUTH_COOKIE_SECURE=false` in `.env.development` so Vite proxies `/api` to the local backend and local HTTP can persist auth cookies instead of inheriting hosted settings from `.env`. Login now verifies `/api/auth/session` before storing the authenticated frontend user or opening the dashboard. Login, session bootstrap, and refresh responses return a CSRF token for frontend `sessionStorage`; unsafe business writes still require the matching backend cookie/header pair. Refresh is recovery-only and skips that header check so a validated, path-scoped HttpOnly refresh cookie can recover a reopened browser session after the prior `sessionStorage` token is gone.
- Invoice persistence now includes additive `Invoice.paidAmount`. API serializers derive `balanceDue` and a display-only finance status with shared `@faako/finance` helpers. This remains manual invoice tracking, not a payment ledger or Paystack reconciliation source of truth.
- `APP_ENV` and `ENFORCE_DATABASE_ISOLATION` are important safeguards for database targeting.
- `OAUTH_TOKEN_ENCRYPTION_KEY` is required when Google Calendar integration is enabled.
- `src/config/adminModules.js` defines the Dev ERP admin module registry for home, dashboard, rent, appointments, customers/organizations, payments, reports, users, profile, and settings.
- `src/app/navigation.js` adapts the registry into the current sidebar and mobile navigation. `src/utils/moduleAccess.js` maps restricted frontend routes to the same module keys used by backend capabilities, preserves the rent-only `/dashboard` landing, and sends custom restricted users to their first allowed module instead of a blocked dashboard loop.
- Registry metadata includes group, status, visibility, and state fields for future grouped rendering and module exposure controls, plus child modules for current detailed routes that should not be consolidated yet.
- Hidden modules are filtered out of sidebar and mobile navigation. Disabled, internal, coming-soon, and experimental metadata is currently visual only and does not block routes, redirect users, or change backend access.
- The app shell uses shared ERP topbar, page-content, mobile-bottom-nav, and status-badge wrappers from `@faako/ui`, but Dev ERP sidebar behavior, auth, notification polling, offline banner, backend capabilities, pages, and workflows remain app-owned.
- Shared shell placeholders for offline/sync/notifications/org switching are available structurally only. Dev ERP live behavior should stay app-owned until backend-owned shell metadata exists.
- Settings now uses low-risk shared ERP panel, panel-header, stack, and form-group wrappers from `@faako/ui`. The wrappers preserve existing legacy class names and do not change alert settings API calls, Sync Review behavior, auth, routes, storage behavior, or live workflows.
- Settings now uses shared `ERPFieldGroup` from the `@faako/ui` form foundation for alert subscription fields. Alert preference state, save/test handlers, API calls, auth/session handling, SMS availability, and Sync Review behavior remain app-owned.
- Settings now uses shared `ERPActionBar`, `ERPPrimaryAction`, and `ERPSecondaryAction` wrappers from the `@faako/ui` modal/action foundation for alert preference buttons. Loading/disabled flags are passed through from the existing Settings state; save/test behavior and API calls remain app-owned.
- System Health now uses shared `ERPTable` and `ERPStatusBadge` presentation components from `@faako/ui` for the read-only service status table. Health data loading, refresh actions, incident-note local storage, status mapping, auth, and API behavior remain app-owned.
- Team consolidation is pending for Dev ERP. User Control and Profile are both team-adjacent, but they have different access assumptions, so they should not be forced under one visible Team module until capability behavior is reviewed.
- Settings consolidation was reviewed and left unchanged. `/settings` is the only current Dev ERP settings/config route. Reports now owns scheduled report-email configuration and manual sends only; System Health and Audit Logs are standalone Insights modules. Audit analytics and CSV export live under Audit Logs, with `/api/reports/summary` retained as a compatibility alias for older frontend deploys but classified under the `audit-logs` backend capability.
- Bookings/Rentals/Schedule consolidation was reviewed and left unchanged. `/bookings` is already nested under Rent as Appointments, and Dev ERP has no separate rentals or schedule route to safely group under a new Bookings module in this low-risk phase.

- Paystack foundation planning is in `paystack-foundation-plan.md`. Current Dev ERP Paystack work is planning/config-only: `.env.example` documents expected server-side env values, and `backend/payments/paystack.config.js` exposes env-key constants plus safe configuration-status metadata without returning secret values. Dev ERP rent payments, operational records, reports, accounting paid state, public invoice tokens, and future receipt ownership remain app-owned until separate implementation work.

Dev ERP consumes it only in Rent and Invoicing currency display helpers; current rent payment, accounting, invoice, report, public-token, and balance behavior remain app-owned.

- Queued rent payment sync marks auth, permission, duplicate, invalid tenant, changed balance, and tenant-scope failures as needs-review placeholders. Staff must treat needs-review payments as unresolved until the server accepts them; no server balance update, notification, accounting/report effect, or final payment record exists while the queue item is pending.

It provides normalizeOrganizationSettings, getOrganizationDisplayName, getOrganizationCurrency, getOrganizationCurrencySymbol, getOrganizationTimezone, getOrganizationBranding, getOrganizationContactInfo, and stripSensitiveOrgSettings. No app code uses it yet — wiring requires a backend /api/org/settings endpoint scoped by authenticated session organizationId. ## Risks to monitor

- Permission mismatches between frontend route guards and backend capabilities.
- Operational record, rent/payment, accounting, invoicing, and reporting calculation drift.
- Integration failures caused by missing encryption keys or environment values.
- Email workflow or AI/productivity endpoint changes affecting real users or records.
- Future registry wiring into access checks, route guards, backend capabilities, database-backed toggles, org-level config, or SaaS plan gating could affect live navigation or permissions and must be reviewed separately.
- Shared shell wrapper changes can affect live topbar spacing, mobile navigation, and operational workflow ergonomics even when data behavior is unchanged.
- Forcing Team grouping before capability review could hide Profile or User Control from live users with restricted module access.
- Forcing future Settings grouping before route/capability review could hide operational monitoring or configuration routes from live users.
- Forcing a Bookings parent before rent-only navigation review could disrupt live users who currently understand Appointments as Rent-adjacent.
- Finance consolidation could disrupt live rent payments, public invoices, reporting, or rent-only users if navigation grouping is mistaken for backend capability enforcement.
- Renaming or exposing the hidden Payments parent too early could confuse current Accounting/Invoicing users or alter rent-only navigation expectations.
- Shared payment or receipt extraction could alter live rent balances, invoice statuses, reports, public invoice token behavior, or accounting summaries if it assumes REEBS-style orders, immutable receipts, or ledger-backed invoices before Dev ERP-specific contracts exist.
- Paystack integration could incorrectly mark invoices paid, duplicate payment records, or create spoofable receipts if webhook signatures, idempotency, provider references, organization scoping, audit logs, and manual reconciliation are not implemented before live payment links.
- Proposal previews could be mistaken for final client-facing workflows if share/PDF/approval boundaries are not kept clear. The current `/proposal/view/:token` client route is token-gated and can store lightweight approval/request-changes responses for shared proposals; approved proposals can create editable invoice drafts from the authenticated admin UI. It does not create digital signatures, payment links, notification sends, version locks, or server-rendered PDFs.
- Shared architecture work could be mistaken for shared runtime behavior; keep Dev ERP rent payment writes, balance calculations, reports, invoice statuses, and public invoice token behavior unchanged until app-specific adapters are proven.
- Shared notification templates could be mistaken for automated delivery. Current Dev ERP use is the user-triggered appointment-link email draft only; do not send automated messages or include internal notes, audit metadata, raw database IDs, secrets, or environment values in customer messages.
- Offline queue constants could be mistaken for broader enabled offline workflows. Dev ERP currently queues new rent payment recording only; it must not queue rent payment edits, inventory adjustments, booking/calendar settings, Google Calendar sync, invoices, reports, accounting changes, or public-token actions until backend permission rechecks and conflict handling exist.
- Queued rent payments may fail when tenant access, balances, permissions, or duplicate payment context changes before sync. The current placeholder keeps failed/needs-review queue items local; do not update server balances, notifications, accounting summaries, or reports offline.
- Sync Review can make local queue state easier to change. Operators should treat retry as a request for existing server validation, and treat cancel/mark-resolved as local housekeeping after manual review, not as a production data write.
- Cleanup work could disrupt live operational data if backend routes, capability checks, rent payments, invoices, reports, public booking, public invoice, email workflows, or AI/productivity endpoints are refactored without dedicated tests and rollback plans.
- Shared form wrappers could be mistaken for shared validation or submit behavior. Keep Dev ERP form state, validation rules, backend checks, auth/session handling, API calls, and workflow side effects app-owned until a dedicated form-by-form review is complete.
- Shared modal/action wrappers could be mistaken for shared confirmation or destructive-action behavior. Keep Dev ERP modal state, cancel/confirm semantics, save/delete/submit handlers, backend checks, auth/session handling, API calls, and workflow side effects app-owned until a dedicated modal/action review is complete.
